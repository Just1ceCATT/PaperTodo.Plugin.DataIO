# PaperTodo DataIO 插件用户数据审查报告

> 审查日期：2026-11-22
> 审查对象：`Z:\tool\PaperTodo.Plugin.DATAIO`（master 分支，含 2 处未提交改动：导入文件过滤器文案、JSON 解析错误文案，均与数据安全无关）
> 审查重点：**PaperTodo中用户数据的生命周期、完整性与丢失风险**。核心标准：本插件能否保证用户数据不会在未经预期的情况下被读取、泄露、篡改、覆盖、删除或丢失。

## 1. 审查范围与方法

- 会话编排：`DataIoSession.cs`、`DataIoPlugin.cs`

严重等级定义：

| 等级 | 含义 |
| --- | --- |
| 🔴 高 | 正常使用路径上即可导致用户数据被覆盖、篡改或永久丢失 |
| 🟠 中 | 特定操作序列或默认设置组合下会发生非预期的数据修改/丢失 |
| 🟡 低 | 边缘条件下的数据变异，或非数据本体的完整性缺口 |
| ⚪ 提示 | 值得知晓的设计限制或最佳实践，不构成直接风险 |

## 2. 用户数据生命周期总览

```
┌─────────── 读取路径（不改变PaperTodo数据）───────────┐
│ PaperTodo API：ListPapers / ListTodos / GetNote        │
│   → 权限门控（papers.read/todos.read/notes.read） │
│   → 仅用于列表、预览、导出快照                     │
│ 文件读取：OpenFileDialog → JsonFiles.ReadAllText    │
│   → 64 MiB 上限，纯内存解析，后台线程              │
└──────────────────────────────────────────────────┘
┌─────────── 写入路径（PaperTodo数据，不可逆）──────────┐
│ 新建：CreatePaper（新纸片 + 初始待办/正文）        │
│ 更新：WriteNote Replace（笔记整体替换）            │
│       UpdateTodo（Done/Order/关联纸片）            │
│       SetTodoReminder                              │
│ 删除：DeleteTodo（更新模式下删除"文件中不存在"的   │
│       本地待办）                                    │
└──────────────────────────────────────────────────┘
┌─────────── 文件写入（用户选择路径，原子替换）────┐
│ JSON：DataFileService.Write                        │
│ Markdown：MarkdownExportService.Write              │
│   → 临时文件 + File.Move 原子替换                  │
└──────────────────────────────────────────────────┘
┌─────────── 插件私有状态（PaperTodo托管 StateJson）────┐
│ UI 偏好 + 导入身份映射（sourceId → 本地纸片 ID）  │
└──────────────────────────────────────────────────┘
```

关键事实：**对PaperTodo数据的破坏性写入只有一条入口——导入**；导出全程只读。破坏性 API（`notes.replace`、`todos.delete`）在 `plugin.json` 中默认申请。

## 3. 发现的问题（按严重度排序）

### 🔴 H-1　Markdown 导出破坏图片引用，更新式回导会永久改写原笔记

**位置**：`Services/MarkdownExportService.cs:108-110`（`AppendNote` 调用 `ImageReferenceScanner.ReplaceWithMissingLabel`）；`Services/MarkdownImportParser.cs:13-16`（marker 保留 `sourceId`）；`Models/DataIoSettings.cs:18`（`UpdateImportedPapers` 默认 true）。

**场景**：
1. 用户此前导入过某文件，本地纸片 L 已登记身份映射（sourceId S → L）；
2. L 的笔记含图片引用 `![...](i:123)`，用户导出为 `.md`——导出文件中该引用已被替换为 `[图片缺失: 123]` 文本；
3. 用户把这份 `.md` 再导入（同一来源）：marker 中的 sourceId 命中身份映射，更新预览中默认选择"更新"，`WriteNote(Replace)` 把**已带"图片缺失"标记的正文写回本地笔记**。

**后果**：原笔记中的图片引用被永久删除，替换为死文本；原图（PaperTodo图片库中的本体）成为孤儿。用户"导出→回导"这一最自然的备份往返，恰恰损坏了数据本体。JSON 路径不受影响（图片引用原样保留在正文中）。

**建议**：
- 更新模式下，若"文件正文"与"上次导入时写入的正文指纹"不一致但差异仅为图片引用替换，应拒绝更新并明确提示；
- 或至少在更新预览的差异视图中高亮"图片引用将被替换为缺失标记"；
- 根本解法：`.md` 导出保留图片引用原文（接受导入端无法显示的代价），把"替换为缺失标记"改为仅提示、不改写。

---

### 🔴 H-2　更新预览默认选择"更新"，且该路径跳过导入前确认摘要

**位置**：`DataIoDialog.xaml.cs:217-226`（`AddChoice` 中 `IsChecked = action == ImportUpdateAction.Update`、`_updateChoices[paper] = ImportUpdateAction.Update`）；`DataIoSession.cs:1189`（`if (_settings.ConfirmBeforeImport && !updatePreviewShown)`——存在更新候选时**跳过**确认对话框）；`DataIoSession.cs:1152-1154`（未命中 choices 时兜底为 Update）。

**场景**：再次导入同一来源文件时，更新预览对话框弹出，每张纸片的默认选项是"**更新**"。用户不逐张审阅、直接点"继续导入"，即触发 `notes.replace`（笔记整体替换）与 `todos.delete`（删除本地新增的待办）——即使被更新的纸片**在本地已被修改过**（仅卡片上一行小字提示"更新会覆盖本地修改"）。同时，本应展示"以下内容无法完整还原"汇总（图片引用、未解析关联、丢弃提醒、截断标题）的确认对话框在此路径下完全不出现。

**后果**：一次"看起来只是确认"的点击即可覆盖本地修改、删除本地待办，且用户未获得与新建路径同等的损失预告。这是全插件中"未经充分预期的覆盖"风险最高的一处。

**建议**：
- 默认选项改为"跳过"或"新增"，把"更新"变成需要显式选择的破坏性动作；
- 或对 `TargetLocallyModified == true` 的纸片强制默认"跳过"；
- 更新路径合并展示确认摘要（复用 `BuildConfirmation` 的汇总内容）。

### 🟠 M-1　导入全程非事务，中途取消/关闭会留下半成品且无记录

**位置**：`DataIoSession.cs:150-171`（`Dispose` 取消 `_operation`）；`Services/ImportService.cs:269-277`（删除本地待办循环中逐条 `ThrowIfCancellationRequested`）。

**场景**：导入进行到一半时用户关闭纸片/切换正文形态 → 会话 `Dispose` 取消令牌 → 正在进行的更新在"删除本地待办"循环中任意位置中断。已创建的纸片、已替换的笔记正文、已删除的部分待办全部保留。

**后果**：PaperTodo数据处于新旧混合的中间态，且**没有任何提示告知用户"导入未完成，数据可能部分应用"**（结果对话框根本不会弹出）。属于结构性限制（PaperTodo无事务 API），但插件未做任何补偿。

**建议**：取消后通过PaperTodo通知机制提示部分应用的状态；至少在 README/设置说明中明确"导入不可中断、中断会产生部分数据"。

---

### 🟠 M-2　单张纸片更新失败时，已部分生效的修改不回滚也不揭示

**位置**：`Services/ImportService.cs:198-288`（`UpdateOneAsync` 顺序：改 Done → 追加 → 删除，各步骤分别检查权限）。

**场景**：以缺 `todos.append` 权限为例：待办纸片更新时，本地匹配项的 Done 状态已被 `UpdateTodo` 修改，随后追加新待办抛出 `permission_denied` → 该纸片计入"失败"。结果对话框显示"失败 1 张"，但**本地数据已被实际修改**，用户无从得知。

**后果**：失败计数掩盖了已发生的数据变异，用户可能误以为本地未被触碰。

**建议**：在 `UpdateOneAsync` 前置检查全部所需权限（append/delete 在改 Done 之前判定），避免"改一半才失败"；失败条目注明"可能已部分应用"。

---

### 🟠 M-3　待办更新按"文本"匹配，同文本多待办会交错覆盖

**位置**：`Services/ImportService.cs:203-245`。

**场景**：更新待办纸片时以 `todo.Text` 为唯一匹配键，同文本多条按 `(Text, Done)` 队列消费。本地有两条"买牛奶"（一条完成一条未完成）、文件中也是两条但完成状态排列不同时，匹配按 Done 兜底（`FindIndex` 失败取 index 0），状态可能交叉错配。此外，**本地用户手工添加的、文本恰好与文件中某条相同的待办会被改状态或删除**。行为在确认文案中有声明（"更新会替换匹配纸片的笔记正文和待办集合"），但 H-2 的默认"更新"放大了误伤概率。

**后果**：数据不被删除但被非预期改写；极端情况下用户自己新增的待办被"对齐"到文件状态。

**建议**：文档化该匹配语义；对"本地存在但文件中没有的同文本待办"的删除增加逐条确认或至少在差异预览中列明。

---

### 🟠 M-4　导出文件不是完整备份：图片本体、第三方插件正文、关联路径、过去提醒均不在文件中

**位置**：`Services/ExportService.cs:100-114`（非 `builtin.markdown` 正文导出为空）；`Services/ImportService.cs:508-514`（LinkedPath 无写入 API）；`Services/ImportService.cs:484-487`（过去提醒丢弃）；`Services/MarkdownExportService.cs`（Markdown 不含 Show/提醒/关联）。

**场景**：用户把"导出"当作完整备份手段（这是插件最自然的用法预期）。导出文件中：图片只有文本引用、本体不导出；由其他插件提供正文的笔记导出为空白；待办关联的文件/文件夹路径丢弃；已过期提醒丢弃；Markdown 格式还额外丢失可见性。

**后果**：PaperTodo数据丢失后无法从导出文件完整还原。UI 各处提示相当充分（结果对话框、预估、确认文案都点名了），故降为"中"——**问题不在隐瞒，而在于插件名称与流程暗示了"数据导入导出"的完整性预期**。

**建议**：在导出完成对话框中用一句话明确"此文件不是完整备份"，或提供"备份完整性清单"。

---

### 🟡 L-1　纸片转换为本插件时，用户原有标题被静默覆盖为"DataIO"

**位置**：`DataIoSession.cs:63-70`。

**场景**：把任意纸片（例如一篇有意义的标题的 Markdown 笔记）的正文切换为本插件 → 标题立即被改为"DataIO"，原标题文本丢失。仅执行一次（`TitleInitialized` 持久化），注释表明是有意为之，但对用户而言是**未经确认的破坏性修改**。

**建议**：仅当原标题为空/为旧插件名时才改名，或在改名前弹一次可跳过的确认。

---

### 🟡 L-2　`ContentAvailable` 为 null 的第三方文件可空正文覆盖匹配笔记

**位置**：`Services/ImportService.cs:178-196`（只拦截 `== false`）。

**场景**：身份映射命中的前提下，导入一份手工构造/第三方工具生成的文件（`format` 与 `schemaVersion` 均可伪造，无签名校验），其中某笔记缺少 `contentAvailable` 字段且 `content` 为空 → 更新会以空正文 `WriteNote(Replace)` **清空本地笔记**。本插件自身导出的文件总是写入 `contentAvailable`，故触发面较窄。

**建议**：更新时将 `ContentAvailable != true` 一律视为不可更新（与 `BuildImportPreview` 的 `ContentAvailable = source.ContentAvailable != false` 口径相比，更新路径更应从严）。

---

### 🟡 L-3　Markdown 往返的正文规范化差异会经更新写回本地

**位置**：`Services/MarkdownImportParser.cs:196-214`（`StripTrailingSeparator` 剥离尾部 `---` 与空行）、`185`（仅 Tab/4 空格续行）。

**场景**：笔记正文以水平分隔线 `---` 结尾 → 导出 `.md` → 回导更新 → 尾部分隔线被剥离后写回，**用户内容被静默裁剪**；缩进不足 4 空格的行在待办分节解析中被丢弃。仅影响 Markdown 路径且需更新模式命中。

**建议**：更新前对比"文件正文"与"上次导入正文"的规范化差异，存在剥离/丢弃时拒绝更新并列明。

---

### 🟡 L-4　状态损坏或超上限时，身份映射静默丢失 → 重复纸片

**位置**：`Models/DataIoState.cs:49-56`（`JsonException` 时整体回退默认值，`ImportLinks` 随之丢弃）、`82,95-97`（`MaxImportLinks = 4096` 静默截断）；`DataIoSession.cs:1216-1246`（导入中途抛非预期异常时 `RecordAsync` 不执行）。

**场景**：状态 JSON 损坏/超限/导入异常中断 → 身份映射缺失 → 下次导入同一文件时按"全部新建"处理，工作区出现整批重复纸片。不丢失已有数据，但违背"更新原纸片"的既定预期，且用户难以理解重复的来源。

**建议**：状态解析失败时保留原 JSON 供诊断（而不是直接覆盖回默认）；`RecordAsync` 前置 try/catch，保证已成功创建的纸片尽可能登记映射。

### ⚪ 提示项

- **无任何网络行为**：全库无 `HttpClient`/WebClient/遥测，数据只在本机内存、PaperTodo API 与用户选择的文件之间流动，无外泄通道。剪贴板复制（`PaperPreviewWindow.xaml.cs:568`）为用户显式点击触发。
- **文件写入采用原子替换**（`JsonFiles.WriteAllTextAtomic`：临时文件 + `File.Move`），断电/异常不会留下半截导出文件；临时文件清理失败不影响主流程。
- **权限门控集中且从严**：所有PaperTodo调用经 `HostGateway` 权限判定 + UI 线程封送；导出为纯读路径；权限缺失时按能力降级并提示，不静默失败。
- **输入上限完备**：64 MiB 文件、200 张纸片、10 万字笔记、5,000 字待办、每纸片 200 条待办、JSON 深度 64，均在上游拦截。
- **空正文覆盖防护**：`ContentAvailable == false` 时更新被显式阻止（"content_unavailable"）；导出侧同样提示"N 张笔记正文不可读取，已按空正文导出"。
- **身份映射使用前校验**：命中映射的更新目标会核对存在性与类型，失效映射自动清理（`ImportIdentityService.ResolveAsync`）；PaperTodo删除纸片事件触发映射同步清理。
- **自我纸片排除**：导出永远跳过 DataIO 工具纸片自身，避免自我复制循环。
- **重复 sourceId 拒绝**：同文件内重复 sourceId 直接判为不可导入，杜绝关联还原歧义。
- **取消语义正确区分**：`CancelInteractions` 明确不中止导入任务（注释交代了纸片失焦的原因），取消仅在会话 Dispose 时发生。

## 4. 结论与修复优先级

插件整体架构是健康的：读写路径分离清晰、PaperTodo调用全部过权限门控、文件写入原子、无网络面、输入上限完备。"读取、泄露、篡改"三个维度基本达标；**风险集中在"覆盖与丢失"维度，且全部汇聚于一条链路——更新式导入**：

```
Markdown 导出改写正文（H-1）
        ↓
sourceId marker 命中身份映射
        ↓
更新预览默认"更新" + 跳过确认摘要（H-2）
        ↓
notes.replace / todos.delete 生效 → 本地数据被覆盖/删除
```

建议按以下顺序修复：

1. **立即**：更新预览默认动作改为"跳过"或"新增"（H-2，改动小、收益最大）；
2. **短期**：Markdown 导出不再改写图片引用，或更新前对比正文规范化差异拒绝带损更新（H-1、L-3）；
3. **短期**：更新纸片前置检查全部权限，杜绝"部分生效再报失败"（M-2）；
4. **中期**：更新路径合并确认摘要；导入中断后提示部分应用状态（H-2 补充、M-1）；
5. **择机**：标题覆盖改为条件触发或加确认（L-1）；`ContentAvailable != true` 从严拦截（L-2）；状态损坏诊断保留（L-4）。
