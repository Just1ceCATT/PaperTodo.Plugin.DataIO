# 导入数据处理策略调查

> 本文记录身份适配层实现前的导入行为，保留作背景调查。当前实现已支持“再次导入时更新已导入的纸片”，详见 [导入身份适配实现](导入身份适配实现.md)。

本文说明 PaperTodo 数据导入导出插件（DATAIO）在身份适配层实现前如何处理导入数据。

## 1. 总体策略

**只追加，不覆盖、不删除任何现有纸片。**

每次导入都会调用PaperTodo `CreatePaper` 创建全新纸片，由PaperTodo生成新 ID。导入文件里的 `sourceId` 只用于同一文件内的关联纸片还原，不会作为PaperTodo ID 使用。

代码位置：

- `Services/ImportService.cs`
- `DataIoSession.ImportAsync`
- `Services/ImportPlanParser.cs`

## 2. 文件读取与解析

### 支持格式

- **JSON**：校验 `format = papertodo.paper-export`、`schemaVersion = 1`。
- **Markdown**：
  - 本插件导出的 Markdown 通过 `<!-- papertodo-dataio:v2 type=todo|note -->` 分节，并兼容旧版 `<!-- papertodo:type=... -->`；代码块内的标记会被忽略；
  - 无标记的普通 Markdown 整份作为一张纸片，首个 `# 标题` 作为标题；
  - 正文只有 `- [ ]` / `- [x]` 列表时识别为待办，否则识别为笔记。

### 预检与限制

解析阶段不接触PaperTodo API，只处理内存数据：

- 单文件最多 **200 张纸片**、单笔记正文 **100,000 字符**、单待办文本 **5,000 字符**、每张待办纸片最多 **200 条待办**、文件最大 **64 MiB**。
- 笔记不能带待办；待办纸片不能带笔记正文。
- `sourceId` 必须唯一，否则整份文件拒绝导入。
- 空待办文本会被移除。
- 标题会去控制字符，过长时预截断；实际导入时若仍超上限，会解析错误信息后截断重试。
- 预检会统计并提示：
  - 文件外关联纸片；
  - 待办关联的文件/文件夹；
  - 已过期提醒；
  - 含图片引用的笔记；
  - 空标题、超长标题等。

### 用户选择

解析后可逐张勾选要导入的纸片，只导入选中部分；未选中的不会创建。

## 3. 第一遍：创建纸片

逐张串行创建：

- 权限要求：`papers.create`；待办纸片还需 `todos.append`，带正文笔记还需 `notes.append`。
- 先检查工作区纸片总数，`现有 + 待导入 > 200` 时整批拒绝。
- 创建内容：
  - 标题（已清洗/截断）；
  - 类型 `todo` / `note`；
  - 可见性：`show = 导入后显示新纸片设置 || 文件中的 show`；
  - 待办纸片：文本 + 完成状态；
  - 笔记纸片：正文。
- **提醒和关联纸片不会在这一步写入**，避免PaperTodo校验失败导致整张纸片创建失败。

### 失败策略

- 单张纸片失败：记录失败项，**继续导入后续纸片**。
- PaperTodo致命错误（会话关闭、程序退出、数据重载、纸片上限）：标记“提前结束”，停止后续创建。
- **没有事务回滚**：已成功创建的纸片会保留。

## 4. 第二遍：还原顺序、关联纸片、提醒

只对待办纸片执行，且受设置项控制。

### 待办匹配

按 **（文本, 完成状态）** 分组建立队列，再按导出顺序逐条匹配新纸片中的待办，而不是按索引匹配。这样可以容忍PaperTodo自动清除已完成待办、自动置底等行为。

### 还原顺序

按文件中的 `order` 重排匹配到的待办。若开启“完成项自动置底/自动清除”，最终顺序仍以自动排序为准。

### 还原关联纸片

- 只还原**同一导入文件内**存在的目标，通过 `sourceId → 新纸片 ID` 映射改写。
- 链接到文件外目标：丢弃并提示。
- 链接到自己：丢弃。
- PaperTodo关闭“启用待办关联纸片”：该批链接全部跳过并提示。

### 还原提醒

只还原满足以下条件的提醒：

- 待办未完成；
- 提醒时间在未来。

已完成待办的提醒、过期提醒都会被跳过。

### 文件/文件夹关联

PaperTodo没有写入路径关联的 API，因此这类数据**一律不还原**，只按纸片汇总提示“N 条待办关联的文件或文件夹，导入后未保留”。

## 5. 冲突与去重

**当前没有任何去重或冲突处理。**

- 不按标题匹配现有纸片；
- 不检查待办文本是否已存在；
- 不覆盖、不合并、不跳过重复项；
- 同一个文件导入两次，会得到两套新纸片。

## 6. 图片来源与限制

- JSON / Markdown 都只保存笔记正文文本，不包含图片本体。
- JSON 保留 `![](i:123456)` 引用；导入后能否显示取决于图片 ID 在本机是否仍有效。
- Markdown 导出原样保留正文中的图片引用文本（如 `![](i:123456)`），保证导出再导入时不会破坏原始正文；图片本体仍不在文件中，换设备或原图被清理后无法显示。
- 旧版插件导出的 Markdown 中的 `[图片缺失: 123456]` 标记会被识别：更新命中本地纸片时强制跳过，避免覆盖本地图片引用。
- 导入结果会提示含图片引用的笔记数量。

## 7. 结果与反馈

导入结果包含：

- 新增纸片 / 失败纸片 / 新增待办数量；
- 还原的关联纸片、提醒数量；
- 逐条警告与失败原因；
- 路径关联未保留的按纸片提示。

导入完成后会清空已选文件，避免误触重复导入，并刷新纸片列表。

## 8. 典型用户场景的现状

| 用户想法 | 当前行为 |
| --- | --- |
| 恢复一份备份 | 会追加一套新纸片，旧纸片仍在 |
| 把两份计划合并 | 得到两张独立待办纸片，不会合并 |
| 反复导入同一文件 | 每次都会产生重复纸片 |
| 用导入文件更新现有笔记 | 不支持，只会新建 |
| 导入到指定纸片 | 不支持，目标不可选 |
| 只导入部分内容 | 支持按纸片勾选 |
| 还原提醒/纸片关联 | 支持，但受设置和PaperTodo能力限制 |
| 还原文件/文件夹关联 | 不支持 |

这也解释了为什么“追加新纸片”之外，**合并到已有纸片、同名合并、去重追加**会是比较符合用户需求的下一步策略；而“覆盖替换”需要额外权限且风险最高。

## 9. 相关设置项

| 设置 | 作用 |
| --- | --- |
| 导入后显示新纸片 | 忽略文件中的可见性，统一显示新纸片 |
| 导入前确认 | 显示纸片数量、类型和无法还原的内容 |
| 还原待办顺序 | 按导出顺序修正 `Order` |
| 还原待办关联纸片 | 只还原同一导入文件内存在的关联目标 |
| 还原提醒 | 只还原未来且未完成待办的提醒 |
